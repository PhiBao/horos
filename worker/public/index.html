Why this is not a filter

A filter reads the invoice and decides whether the address looks suspicious. That is a losing game: the address is new to every system that ever sees it, because the attacker generates it. Horos does not score the address. It refuses to name one.

CustodyVault.pay(counterpartyId, amount, reference)

There is no parameter for a destination. The vault asks the registry which account this counterparty is currently paid at, and sends there. Paying a new address is not a call this contract can be given, so no prompt, no compromised key and no bug in this page can express it. The refusal is a property of the interface rather than a check that ran.

Changing the address is a ceremony

When a supplier genuinely moves accounts, the move requires two signatures that the recipient cannot produce: the account that was last paid, agreeing to be replaced, and the business, agreeing to the change. Until both exist, the new account is a proposal — visible, pending, and unable to receive anything.

If the old key is genuinely lost, that is not a dead end and it is not a silent override either. The counterparty page shows what happened: the change is recorded permanently and the counterparty is marked broken, in public, where everyone who might pay it can see.

This page holds no key

It reads Arc over public RPC endpoints, which reject every write by design. The ABI it is compiled against contains no write function (worker/src/abi.ts). The decision logic is not reimplemented here — this Worker imports lib/policy.ts from the repository, the same file the unit tests run against, so the deployed site and the test suite cannot disagree.
